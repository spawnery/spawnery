# Milestone 6e — CI

## 1. What this milestone is

This repository has no CI. Every check it has — `make test`, `make lint`,
`make e2e`, `make image-repro`, `hack/publish.sh` — runs when somebody
remembers to run it, on one machine, under one container runtime. Milestone 6
has been parking work here since 2c: `docs/known-issues.md` says of the
`deps.json` drift guard that "the check belongs with CI in milestone 6", and
of the toolchain-version coupling that "the standing check still does not
exist, and belongs with the `deps.json` guard above."

6e wires GitHub Actions. Three workflows, four blocking checks on every pull
request, one nightly, one on a version tag.

**What it does not establish**, stated first: CI does not make an unproven
thing proven. `make e2e` will run on a hosted runner under Docker, which is a
second independent execution of the same script — and from that point
**nothing automatic exercises the rootless-podman path this project has used
until now.** CI proves Docker; the repository owner's machine proves podman;
neither proves the other. That is a trade this milestone makes deliberately,
not a gap it overlooked.

## 2. The three workflows

| File | Trigger | Jobs |
|---|---|---|
| `.github/workflows/ci.yml` | push to `master`, every pull request | `test`, `lint`, `deps`, `e2e` — four separate jobs |
| `.github/workflows/nightly.yml` | cron, plus `workflow_dispatch` | `make image-repro` |
| `.github/workflows/release.yml` | push of a `v*` tag | `hack/publish.sh` with `WRITE_DIGEST=1` |

Four separate jobs rather than four steps in one, for two reasons: a failure
names itself in the checks list without anyone opening a log, and the three
fast checks do not queue behind `make e2e`'s cluster.

The nightly runs at `17 3 * * *` — 03:17 UTC. The odd minute is deliberate:
the top of an hour is when every other repository's cron fires, and a job
that waits in a queue for its runner is a job whose duration measures the
queue rather than the build.

`workflow_dispatch` on the nightly is not decoration — it is how the nightly
gets driven once during this milestone, since waiting for a cron to prove the
workflow works is not a test.

### 2.1 Nix on the runner, and one decision deferred to a measurement

Every job needs `nix develop`: nothing in this repository — `go`, `helm`,
`kind`, `kubectl`, envtest's API server binaries — is on `PATH` without it.

Installing Nix is settled. **Caching the store is not, and this design
deliberately does not decide it.** The landscape of Nix caching actions has
moved more than once, and betting a milestone on a third-party cache service
whose terms may have changed is worse than a slower first implementation.

So: **Task 1 measures the cold run without any store cache and records the
number.** If it is tolerable, that is the design — one fewer dependency on
somebody else's service. If it is not, the cache goes through GitHub's own
`actions/cache` keyed on `flake.lock`, not through a third party.

This is an open decision with a named measurement point and an owner, not a
placeholder. The plan carries the measurement as a step and the result goes
into the task report.

### 2.2 The provider, which is better news than it looks

`hack/e2e.sh` is provider-agnostic. The rootless-podman invocation appears
only in a comment at `hack/e2e.sh:11-16`, documenting how the *caller* invokes
it on the author's machine — `systemd-run --scope --user … env
KIND_EXPERIMENTAL_PROVIDER=podman make e2e`. Nothing inside the script names
podman. On a hosted runner with Docker present, plain `make e2e` is expected
to work unchanged.

**Expected, not known.** No run has happened. If it turns out the script does
need a change, that change is in scope and belongs in the E2E task with its
reason recorded — but the design's assumption is that it does not.

## 3. What each check proves, and what it does not

- **`make test`** — unit tests, envtest, and `chart-lint`, under `-race`.
  One thing this milestone must not let CI overstate: milestone 6d **measured**
  that `chart-lint` catches neither half of a typo'd `{{ .Release.Namespace }}`
  — Helm renders an unresolved `.Release` field as empty and both `helm lint`
  and `helm template` exit 0. It is a syntax-and-render check, and running it
  on every pull request does not make it more than that.
- **`make lint`** — blocking, after §4's cleanup, and with the configuration
  §4 explains is not optional.
- **The `deps.json` guard** — `make agent-deps`, then `git diff --exit-code`.
  It pays off a debt open since milestone 2c. It is also **the only check here
  that can go red for reasons outside this repository**: `make agent-deps`
  reaches Maven Central. An outage there, or an upstream artifact moving,
  produces a drift nobody caused. That is inherent to what the check is, and
  naming it now is what stops the first such failure being read as a
  regression.
- **`make e2e`** — eighteen scenarios, a real kind cluster, a real
  `helm install` into `platform-system`. See §1 for what it costs.
- **Nightly `make image-repro`** — turns milestone 6a's acceptance criterion 2,
  the bit-identical rebuild, from a thing measured once into a thing measured
  continuously. It does not block, because a nightly failure says nothing
  about the code proposed today.

### 3.1 A consequence this milestone should budget for rather than discover

CI runs the suite far more often than a person does, so it will surface flakes
that already exist. One is already known and recorded: milestone 6d saw
`TestARecreatedOrdinalCreatesItsPodOnceThePredecessorIsGone` fail once, pass in
isolation and pass on rerun, and `docs/known-issues.md` carries it. There will
be more.

**A red run in the first weeks is a measurement, not a regression.** The
documents say that before it happens, so the first response is to record the
flake rather than to hunt a change that did not cause it.

## 4. The lint cleanup, and the count that was wrong

`make lint` is red today. **The number is 33, not 17**, and how that was
established matters more than the number.

**Corrected after the milestone's final review: 33 was also wrong.** It was
measured against a `golangci-lint` cache warmed before five further
`SA1019` findings in `internal/controller/setup.go` were known to exist.
CI's own first cold-cache `lint` run found them, and `golangci-lint cache
clean` followed by a plain run reproduces them locally. The true figure,
from a cleared cache, is **38**, not 33 — see `docs/known-issues.md`, "From
milestone 6e", for the full account.

Three separate runs of `make lint` each reported exactly 17 issues while
naming **different files each time**. There is no `.golangci.yml` in the
repository, so golangci-lint's defaults apply, and `max-same-issues` defaults
to 3: at most three findings sharing a message text are shown per linter. The
package walk is concurrent, so which three survived varied per run. Running
with `--max-issues-per-linter=0 --max-same-issues=0` gives the real figure:

- **26 `errcheck`** — unchecked returns, almost all `Close()` and
  `fmt.Fprint*`.
- **7 `staticcheck`** — four `QF1008` (an embedded `Time` field in a
  selector), one `QF1001` (De Morgan), one `SA4006`, one `SA1019`.

Twelve of the 33 are in `_test.go` files. By package: `internal/controller` 7,
`cmd/spawnery-stubop` 5, `cmd/spawnery-join` 5, `internal/mcjoin` 4,
`cmd/spawnery-config` 4, `internal/agentserver` 3, `internal/slp` 2,
`cmd/spawnery-slp` 2, `api/v1alpha1` 1.

**Corrected after the milestone's final review.** The true total is 38, not
33 (see the marker above). The five additional findings are all `SA1019` in
`internal/controller/setup.go`, none of them in a `_test.go` file, so this
paragraph should read: twelve of the **38** are in `_test.go` files, and
`internal/controller`'s own share is **12**, not 7 — every other package's
count above is unchanged.

**A `.golangci.yml` is therefore part of this milestone, and it is not
housekeeping.** With the defaults, CI reports a different subset every run; a
contributor fixes three findings and sees three others appear that were
already there; and no one can tell whether a falling count means the code
improved or the truncation rolled differently. `max-issues-per-linter: 0` and
`max-same-issues: 0` are what turn `make lint` into a measurement. Pinning the
enabled linters in the same file is what stops a toolchain bump silently
changing what "green" means.

**Two of the 33 need judgement and must not be silenced:**

- `SA4006` at `internal/controller/proxygroup_controller_test.go:476` — a
  `group` value is created and never used. That is a test smell, not a lint
  annoyance: either an assertion is missing or the line is left over. It gets
  understood, not deleted.
- `SA1019` at `api/v1alpha1/groupversion_info.go:32` — `scheme.Builder` is
  deprecated and controller-runtime offers no drop-in replacement. Most likely
  a `//nolint:staticcheck` carrying a reason. **The reason is the deliverable**,
  not the directive: it must say what the replacement would be and why it is
  not taken here.

**Corrected after the milestone's final review.** Two of the **38** — not
33 — needed this narrower kind of judgement, a `//nolint` decision made and
documented rather than silently applied. The five further findings this
milestone's own paperwork initially missed did not take that path at all:
they were a second `SA1019`, on the deprecated `mgr.GetEventRecorderFor`,
and closing them forced a real migration off `record.EventRecorder` rather
than a `//nolint` — see `docs/known-issues.md`, "From milestone 6e".

## 5. Publishing, and where the digest goes

On a `v*` tag, `hack/publish.sh` pushes the three images to
`ghcr.io/spawnery/` and, with `WRITE_DIGEST=1`, produces the operator image's
digest. `GITHUB_TOKEN` with `packages: write` authenticates to ghcr for this
repository's own packages. The script already has `DRY_RUN=1`, which builds
and prints what would be copied without needing a credential — which is how
the workflow gets exercised before a real tag exists.

This closes milestone 6a's acceptance criteria 7 and 8, which have been open
since 6a because no real `make publish` had ever run and no digest in a
shipped manifest had ever resolved.

**The digest is emitted, not committed.** It goes into the GitHub Release body
and a job output; the repository owner puts it into
`charts/spawnery/values.yaml`.

The reason is not convenience. The alternative gives a CI job write access to
the default branch, needs a loop-brake against the commit it would itself
trigger, and collides with any branch protection added later. The cost of the
chosen shape is stateable and small: between the tag and the owner's commit,
the chart still carries the previous digest, and 6a's criterion 8 closes with
that manual step rather than without one.

`hack/publish.sh`'s `WRITE_DIGEST` path has never run against a real registry
— milestone 6d exercised its substitution against scratch copies only. So the
first real tag is also the first real test of that path, and the workflow
must fail loudly rather than continue if it does not produce a digest.

## 6. Facts this design asserts about the code already here

Each is a claim an implementer can check before trusting anything above.

1. There is no `.github/` directory and no `.golangci.yml`.
2. `make lint` runs `golangci-lint run` (`Makefile:81-82`) with no
   configuration file, and is not a dependency of `make test`
   (`Makefile:64`).
3. `golangci-lint run --max-issues-per-linter=0 --max-same-issues=0` reports
   **33** issues: 26 `errcheck`, 7 `staticcheck`. Plain `make lint` reports
   17, and the subset varies between runs.

   **Corrected after the milestone's final review.** This fact was measured
   against a stale `golangci-lint` cache and is wrong on two counts. The
   true figure, from a cleared cache, is **38** issues (26 `errcheck`, 12
   `staticcheck`), not 33. And the second sentence's "varies between runs"
   was observed once, during this design's own investigation, and did not
   reproduce when a reviewer later ran the same plain command three
   consecutive times against the same tree and got the identical seventeen
   each time — see `docs/known-issues.md`, "From milestone 6e".
4. `hack/e2e.sh` names podman only in a comment at `:11-16`; no line of the
   script selects a container provider.
5. `hack/publish.sh` reads `DRY_RUN`, `FORCE` and `WRITE_DIGEST` from the
   environment (`:34-36`), and `WRITE_DIGEST=1` writes
   `charts/spawnery/values.yaml`'s `image.digest`.
6. `make agent-deps` (`Makefile:94-95`) runs a Nix-built update script that
   reaches Maven Central, which is why it cannot run inside a Nix build.
7. `make test` (`Makefile:64`) depends on `manifests generate fmt vet
   chart-lint` and runs `go test -race ./... -coverprofile cover.out`.
8. `make image-repro` (`Makefile:170`) builds the three images and compares.
9. `internal/rbacaudit`'s tests require `helm` on `PATH`
   (`internal/rbacaudit/deploy_envtest_test.go`'s `renderChart`).
10. `docs/known-issues.md` carries the `deps.json` guard as belonging to CI in
    milestone 6, and carries the observed flake in
    `TestARecreatedOrdinalCreatesItsPodOnceThePredecessorIsGone`.

## 7. What 6e does not do

- **No chart publishing.** No `helm push` to an OCI registry, no chart
  repository. Milestone 6d's spec called that "6e's or the repository
  owner's"; this milestone's scope chose images. That is a decision rather
  than an omission, and §8 of the handover records where it would go.
- **No RKE2 rollout.** That is the end of milestone 6 and the owner's.
- **No `helm upgrade` test.** Unchanged since 6d: designed and unobserved.
- **No self-hosted runner**, with the consequence §1 states about the podman
  path.
- **No fixing of the flake.** It is recorded, and CI will tell us how often it
  actually fires — which is the information needed before fixing it.

## 8. Acceptance

1. `ci.yml` green on a real pull request, all four jobs.
2. `make lint` blocking, zero findings, with `.golangci.yml` pinning
   `max-issues-per-linter: 0`, `max-same-issues: 0` and the enabled linters —
   and exactly one `//nolint`, the `SA1019` one, carrying a reason that names
   the alternative.
3. The `deps.json` guard runs, and is **deliberately made red once** by
   perturbing `agent/paper/deps.json`, with the failure output recorded.
4. `make e2e` green on a hosted runner under Docker, eighteen scenarios,
   `theOperatorWasNeverDenied` last and passing.
5. The nightly workflow driven once via `workflow_dispatch` and green.
6. `release.yml` exercised with `DRY_RUN=1`, showing what it would push.
7. The cold-run duration measured and recorded, with the store-cache decision
   of §2.1 taken from that number and written down.
8. No document claims CI proves anything it does not — in particular not about
   `chart-lint`, not about the podman path, and not about `helm upgrade`.
