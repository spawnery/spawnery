# Phase 3a: the tutorial Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A reader with no Spawnery knowledge and no cluster gets from an empty machine to standing on a server the operator created — and the path they follow is the path CI drives, so it cannot rot.

**Architecture:** `docs/tutorial/` carries the page and the two files a reader applies: a `kind` cluster config and one manifest holding the `Network`, one `ServerGroup` and one `ProxyGroup`. `hack/e2e.sh` creates its cluster from that same `kind` config, so the port mapping a reader needs exists in CI too and one cluster serves both. A new end-to-end scenario applies the tutorial's manifest, waits for a backend, and joins it with `cmd/spawnery-join --hold` — which is why the tutorial's proxy runs `onlineMode: false`.

**Tech Stack:** kind, Helm, `cmd/spawnery-join`, the existing `test/e2e` harness, MkDocs.

**Spec:** `docs/superpowers/specs/2026-09-15-documentation-show-before-explain-design.md`

## Global Constraints

- **Everything committed is English:** page text, commit messages, comments, manifests.
- **Conventional Commits with a scope**, subject says what changed, body says why, wrapped at 72 columns, ending with the session's two attribution lines.
- **Comments must earn their place.** Default: no comment. Only foreign-system behaviour invisible in the code, a deliberate absence, an otherwise-arbitrary number, or why the obvious approach was not taken.
- **The tutorial shows real output.** Every command on the page is followed by what it actually printed in a run somebody made, not by a description of what it would print. If you did not run it, it does not go on the page.
- **One path, no branches.** No "you could also", no alternative expose strategy, no second group. The guides exist for that.
- **Nix reads the git index** — `git add` new files before any build.
- **Every command runs as `nix develop -c <command>`** from the repository root, no `cd` before the `nix`.
- **This is the development VM** (8 cores, 8 GB, no swap). `make e2e` needs `systemd-run --scope --user --property=Delegate=yes -- nix develop -c env KIND_EXPERIMENTAL_PROVIDER=podman TMPDIR="$HOME/.cache/spawnery-tmp" make e2e` here; read the memory of how e2e is invoked before the first run rather than after a failure.
- **Check gpg before committing:** `echo probe | gpg --pinentry-mode error --local-user "$(git config user.signingkey)" --clearsign >/dev/null` exits 0 when the key is cached and cannot open a prompt. Non-zero means stop and report BLOCKED — pinentry has only the TTY on this machine and a wrong attempt costs the user their session.

### Task 1: The two files a reader applies

**Files:**
- Create: `docs/tutorial/kind-config.yaml`, `docs/tutorial/network.yaml`

**Interfaces:**
- Consumes: `config/samples/network.yaml` as the starting point — read it first; it is a realistic network and this is a stripped one.
- Produces: the two paths Task 2 (`hack/e2e.sh`), Task 3 (the e2e scenario) and Task 4 (the page) all name.

- [ ] **Step 1: Write `kind-config.yaml`**

A reader on `kind` cannot reach a `NodePort` without a port mapping, so this file is not optional scaffolding — it is the reason the tutorial can end with a join at all. `hack/e2e.sh` today runs `kind create cluster --name "$CLUSTER" --wait 120s` with no `--config`, which is why the existing suite has never reached a proxy from outside.

One control-plane node, one `extraPortMappings` entry taking a fixed host port to the proxy's node port. Pick the node port explicitly in `network.yaml` rather than letting Kubernetes allocate one, because a mapping cannot point at a port nobody can predict — and say that in a comment, since a fixed `nodePort` otherwise looks like a novice mistake.

- [ ] **Step 2: Write `network.yaml`**

Start from `config/samples/network.yaml` and cut it to one path: the namespace, the forwarding secret, one `Network`, one `Ephemeral` `ServerGroup`, one `ProxyGroup`. Differences that matter:

- **`spec.config.onlineMode: false` on the `ProxyGroup`** — the custom resource field, not a `configOverlay`. `internal/render` reasserts the keys it owns after merging an overlay, so the CR is the only place online-mode can be moved from. This is what lets `cmd/spawnery-join` finish, and a reader's own licensed client connects to an offline-mode proxy perfectly well.
- **`expose` is `NodePort`** with the fixed port from Step 1.
- **Resources.** The sample asks 2Gi for a Paper server, and that number is not arbitrary — `MaxRAMPercentage=75` leaves only 256 MiB outside the heap at 1Gi and the first join OOMs. Keep 2Gi, and note on the page (Task 4) what the reader's machine therefore needs free, because a tutorial that gets OOM-killed on a laptop is worse than one that says up front what it costs.
- **`minReplicas: 1`** and a `spareSlots` low enough that one join does not immediately start a second server. The tutorial's last step is a reader watching the group react; make that legible rather than a stampede.

- [ ] **Step 3: Check the manifest is accepted, without applying it**

```bash
nix develop -c kubectl apply --dry-run=server -f docs/tutorial/network.yaml
```

Expected: every object `(server dry run)`. **Dry run only.** Do not apply this to the cluster this machine's kubeconfig points at — that is the live `paulwtf` cluster, and it is Flux-managed.

If no cluster is reachable, `--dry-run=client` and say so in the report.

- [ ] **Step 4: Commit**

```bash
git add docs/tutorial/
git commit -m "docs(tutorial): the two files a reader applies"
```

### Task 2: One cluster serves both

**Files:**
- Modify: `hack/e2e.sh`

**Interfaces:**
- Consumes: `docs/tutorial/kind-config.yaml` from Task 1.
- Produces: an e2e cluster whose proxy node port reaches the host, which Task 3 needs.

- [ ] **Step 1: Read what the script does around cluster creation**

`hack/e2e.sh:142` is `kind create cluster --name "$CLUSTER" --wait 120s`. Read the surrounding lines, including the memory-budget comment near line 44 — that comment reasons about the peak of two things, and adding a port mapping should not invalidate it. Say in your report whether it does.

- [ ] **Step 2: Create the cluster from the tutorial's config**

Pass `--config docs/tutorial/kind-config.yaml`. The point is not convenience: it is that the file a reader uses and the file CI uses are the same file, so a mapping that stops working for one stops working for the other. That is the same argument phase 2 made for generated pages, applied to a cluster.

Add a comment saying exactly that, because a path from `hack/` into `docs/` looks wrong at a glance and a reader deserves the reason before they "fix" it.

- [ ] **Step 3: Prove the existing suite still passes**

This is the step that matters. You are changing how every e2e run's cluster is created.

There is a specific risk here rather than a general one: kind runs under **rootless podman** on this machine, and a host port mapping is the part of that combination most likely to behave differently from rootless Docker. If the mapping does not come up, that is a finding about the environment and belongs in the report — do not work around it by dropping the mapping, because the mapping is the reason a reader can join at all.

```bash
systemd-run --scope --user --property=Delegate=yes -- \
  nix develop -c env KIND_EXPERIMENTAL_PROVIDER=podman \
  TMPDIR="$HOME/.cache/spawnery-tmp" make e2e
```

Expected: the whole suite green, as before your change. Record the run's tail. If it fails, the port mapping is not the innocent addition it looks like and you should report that rather than working around it.

- [ ] **Step 4: Commit**

```bash
git add hack/e2e.sh
git commit -m "test(e2e): the cluster comes up the way the tutorial says it does"
```

### Task 3: CI walks the tutorial's path

**Files:**
- Create: `test/e2e/tutorial_test.go`
- Modify: `flake.nix` or `hack/e2e.sh` if `spawnery-join` is not already on the path the suite runs with — establish which, do not assume

**Interfaces:**
- Consumes: `docs/tutorial/network.yaml`, the port mapping from Task 2, and `cmd/spawnery-join`.
- Produces: the run whose output Task 4 puts on the page.

- [ ] **Step 1: Read the harness before writing a line**

`test/e2e/e2e_test.go` has `applyManifest(t, rel string, opts ...client.CreateOption)`, which takes a **repository-relative path** — so `docs/tutorial/network.yaml` needs no copying. `lifecycle_test.go:34` already calls it with `config/samples/network.yaml` and `client.DryRunAll`; you are doing the same thing without the dry run. Read `eventually(...)` and follow one existing scenario end to end before adding yours.

- [ ] **Step 2: Write the scenario**

In order: apply the tutorial's manifest; wait for the `ServerGroup` to report a `Ready` backend; wait for the `ProxyGroup` to be addressable; then join.

```go
// spawnery-join is the automated half of milestone 3's success criterion:
// it logs in far enough to be routed to a backend and answers with an exit
// code. --hold keeps the connection open, which is the only way the proxy's
// status.connectedPlayers is non-zero when the next assertion reads it.
```

Then assert what a reader is told to expect: `status.connectedPlayers` on the `ProxyGroup` reaches 1.

**`spawnery-join` needs `onlineMode: false`**, which Task 1 put in the manifest. If the join fails with an encryption-handshake error, that field is the first thing to check.

- [ ] **Step 3: Establish how the test reaches the binary**

`spawnery-join` is a flake package (`flake.nix`) and ships in no image. Find out whether the e2e run already has it on `PATH` — the dev shell may or may not carry it. If it does not, the smallest honest fix is adding it to the dev shell, not building it inside the test. Report which you found and what you did.

- [ ] **Step 4: Run it**

```bash
systemd-run --scope --user --property=Delegate=yes -- \
  nix develop -c env KIND_EXPERIMENTAL_PROVIDER=podman \
  TMPDIR="$HOME/.cache/spawnery-tmp" make e2e
```

Expected: the suite green including your scenario. **Capture the whole run's output and keep it** — Task 4 needs the real `kubectl` output from this cluster, and re-running to get it later costs another eight minutes.

`E2E_KEEP=1` keeps the cluster and prints its `KUBECONFIG`, which is the cheap way to collect the output Task 4 needs without a second full run.

- [ ] **Step 5: Prove it fails when it should**

In a **throwaway worktree**, set `onlineMode: true` in the tutorial's manifest and confirm the scenario fails at the join rather than passing or hanging. That is the one assertion in this plan that could silently become a no-op, because a test that never reaches the join still looks green if it only checks what came before. Record the failure. Remove the worktree.

- [ ] **Step 6: Commit**

```bash
git add test/e2e/tutorial_test.go
git commit -m "test(e2e): the tutorial's path is driven, join included"
```
