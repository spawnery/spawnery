# Milestone 6e — CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire GitHub Actions — four blocking checks on every pull request, one
nightly, one on a version tag — and make `make lint` a check that can be
trusted.

**Architecture:** Three workflow files, each job running `nix develop -c
<make target>` so CI runs exactly what a developer runs. The lint cleanup
comes first, because a blocking check cannot be added to a red target, and a
`.golangci.yml` comes before the cleanup, because without it the list of
findings is truncated and unstable.

**Tech Stack:** GitHub Actions on hosted runners, Nix flakes, Go 1.24, kind
under Docker, Helm, skopeo.

**Spec:** `docs/superpowers/specs/2026-08-19-ci-design.md`

## Global Constraints

- **Every local command runs inside the dev shell**, and this machine needs
  the experimental flags:
  `nix --extra-experimental-features 'nix-command flakes' develop -c <cmd>`.
  This plan writes the short form `nix develop -c <cmd>`; expand it every
  time. Nothing — `go`, `helm`, `kind`, `kubectl`, `golangci-lint`, envtest's
  binaries — is on `PATH` without it.
- **A GitHub Actions workflow cannot be verified locally.** There is no
  substitute: `act` emulates neither kind nor the Nix installation credibly.
  Every task that builds a job **pushes the branch to `origin` and watches the
  run**, with `gh run watch` / `gh run view --log-failed`. A task that
  claims a job works without a run ID to point at has not finished. Push the
  working branch — do not push to `master`, and do not merge anything.
- **`make test` runs with `-race`.** Green without it and red with it is red.
- Commit messages use Conventional Commits — `ci(6e):`, `fix(6e):`,
  `docs(6e):`, `chore(6e):` — deliberately overriding this repository's older
  sentence-style history. Every commit ends with exactly these two trailers:
  ```
  Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_014xc1DzU4wwe2h1bV5V7zpn
  ```
- **The real lint figure is 33, not 17.** Plain `make lint` prints 17 and a
  *different* seventeen each run: there is no `.golangci.yml`, golangci-lint's
  `max-same-issues` defaults to 3, and the package walk is concurrent. Until
  Task 2 lands the config, **use
  `golangci-lint run --max-issues-per-linter=0 --max-same-issues=0`** for any
  count you intend to trust.
- **No claim that CI proves something it does not.** Three in particular:
  `chart-lint` catches neither half of a typo'd `{{ .Release.Namespace }}`
  (milestone 6d measured it); nothing automatic exercises the rootless-podman
  path once `make e2e` runs under Docker; and no `helm upgrade` runs anywhere
  in this project.
- **A red run in the first weeks is a measurement, not a regression.** One
  flake is already recorded —
  `TestARecreatedOrdinalCreatesItsPodOnceThePredecessorIsGone`. If a run goes
  red for something your task did not touch, record it and say so; do not
  hunt a change that did not cause it.

### Task 1: One job, and the number that decides the cache

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: nothing.
- Produces: a `ci.yml` with one job, `test`, whose shape Tasks 4 and 5 copy —
  the same checkout, the same Nix installation, the same `nix develop -c`
  invocation. Later tasks add jobs beside it and must not restructure it.

This task exists first because it de-risks the whole milestone: if
`nix develop` is unworkable on a hosted runner, nothing else in this plan
matters, and that is worth learning in task one rather than task five.

- [ ] **Step 1: Read what you are wiring**

```
nix develop -c grep -n "^test:" -A 2 Makefile
nix develop -c cat flake.nix | head -60
```

`make test` (`Makefile:64-65`) depends on `manifests generate fmt vet
chart-lint` and then runs `go test -race ./... -coverprofile cover.out`. It
needs `controller-gen`, `helm`, and envtest's API server binaries — all from
the flake's default dev shell.

- [ ] **Step 2: Write the workflow**

```yaml
name: CI

on:
  push:
    branches: [master]
  pull_request:

# A second push to the same branch cancels the first: nothing here needs the
# older run's answer, and the runners are shared.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    # make test runs manifests, generate, fmt, vet and chart-lint before
    # go test -race across every package, several of which are envtest-backed
    # and start a real API server. Ten minutes is roughly double what it takes
    # on the author's machine.
    timeout-minutes: 25
    steps:
      - uses: actions/checkout@v4

      - name: Install Nix
        uses: cachix/install-nix-action@v27
        with:
          extra_nix_config: |
            experimental-features = nix-command flakes

      # Timed on purpose. The store is cold on every hosted runner, and this
      # number is what decides whether a cache is worth its dependency --
      # see the design's §2.1.
      - name: Warm the dev shell
        run: |
          start=$(date +%s)
          nix develop -c true
          echo "dev shell ready in $(( $(date +%s) - start ))s"

      - name: make test
        run: nix develop -c make test
```

Check `cachix/install-nix-action`'s current major version before you commit
this — pin whatever is current rather than trusting the `v27` written here,
and say in your report which you used and how you checked.

- [ ] **Step 3: Push the branch, open a draft pull request, and watch the run**

**Pushing the branch on its own triggers nothing.** The workflow's `push`
trigger is limited to `master`, and its other trigger is `pull_request` — so
until a pull request exists, a push to `milestone-6e` produces no run at all
and you will sit waiting for one. Open the PR in this step and every later
task's push updates it.

```
git add .github/workflows/ci.yml
git commit
git push -u origin HEAD
nix develop -c gh pr create --draft --fill --base master
nix develop -c gh run watch --exit-status
```

Draft, because nothing here is ready to merge and a draft says so. Record the
PR number — every later task refers to the same one, and acceptance
criterion 1 is "green on a real pull request", which this is.

This is the only way to verify a workflow. Expected: the job goes green.

- [ ] **Step 4: If it fails, read the log before changing anything**

```
nix develop -c gh run view --log-failed
```

Three failures are plausible and each has a different answer. A Nix
installation error is a version pin. A missing binary inside `nix develop`
means the flake's dev shell does not provide something the Makefile assumes
was ambient — report that as a finding, because it is also true locally and
merely hidden by the author's environment. A timeout means Step 5's number is
the answer, not a larger `timeout-minutes`.

- [ ] **Step 5: Record the two numbers**

From the green run, record: the "dev shell ready in Ns" line, and the total
job duration (`gh run view` shows it). Both go in your report.

**Then take the decision the design defers to this measurement.** The
design's §2.1 says: if the cold cost is tolerable, ship without a store
cache — one fewer dependency on somebody else's service; if it is not, cache
through GitHub's own `actions/cache` keyed on `flake.lock`, not through a
third party.

**Tolerable is your judgement and you must state it as one**, with the number
beside it. A dev shell that is ready in under two minutes on a job that runs
for fifteen is noise. One that takes eight is most of the job. If you add the
cache, push again and record the second number so the report shows what it
bought.

- [ ] **Step 6: Commit and report**

Subject: `ci(6e): one job, and the cold-start number behind the cache
decision`. The body carries the two durations and the cache decision with its
reason.

### Task 2: `.golangci.yml`, and the 26 unchecked returns

**Files:**
- Create: `.golangci.yml`
- Modify: fourteen Go files, listed in Step 3

**Interfaces:**
- Consumes: nothing.
- Produces: a `.golangci.yml` that makes `golangci-lint run` report every
  finding on every run, and a tree with zero `errcheck` findings. Task 3
  finishes the job with `staticcheck`; Task 4 makes the target blocking.

**The config comes first, and that ordering is the point.** With
golangci-lint's defaults an implementer sees seventeen findings, fixes them,
runs again, and sees more — findings that were always there and were
truncated away. Fixing a list you cannot see the end of is how this ends up
taking three passes.

- [ ] **Step 1: Write `.golangci.yml`**

```yaml
# Without this file golangci-lint applies its defaults, and the default
# max-same-issues is 3: at most three findings sharing a message text are
# shown per linter. The package walk is concurrent, so *which* three survive
# varies between runs. Three consecutive runs during milestone 6e's design
# each reported exactly 17 issues and each named a different set of files;
# the real figure was 33. A check whose output is a varying sample is not a
# measurement, and CI would have reported a different subset every run while
# nobody could tell whether a falling count meant better code.
version: "2"

linters:
  # Named rather than inherited, so that a toolchain bump cannot silently
  # change what "green" means here. These two are what the tree was already
  # being held to; adding more is a decision for a later milestone, taken
  # with the count it would introduce.
  default: none
  enable:
    - errcheck
    - staticcheck

issues:
  max-issues-per-linter: 0
  max-same-issues: 0
```

Check that key layout against the golangci-lint version the flake pins —
the schema has changed between major versions, and a config the tool ignores
is worse than none. `nix develop -c golangci-lint version` tells you which,
and `nix develop -c golangci-lint config verify` validates the file if that
subcommand exists in your version. Report what you ran.

- [ ] **Step 2: Confirm the config changed what is reported**

```
nix develop -c golangci-lint run 2>&1 | tail -5
```

Expected: 33 issues, 26 `errcheck` and 7 `staticcheck` — the same figure the
explicit flags produced before the config existed. If you get 17, the file is
not being read.

- [ ] **Step 3: Fix the 26 `errcheck` findings**

The complete list, from
`golangci-lint run --max-issues-per-linter=0 --max-same-issues=0`:

```

cmd/spawnery-join/main_test.go:53              conn.Close
cmd/spawnery-slp/main.go:69                    fmt.Fprintf
cmd/spawnery-slp/main_test.go:53               conn.Close
cmd/spawnery-stubop/main.go:197                fmt.Fprintln

internal/agentserver/proxy_envtest_test.go:65  conn.Close
internal/agentserver/server_envtest_test.go:76,621  conn.Close
internal/controller/sample_manifest_test.go:47 f.Close
internal/mcjoin/mcjoin.go:276                  c.Close

```

Line numbers shift as you edit. Re-run the linter rather than working down a
stale list.

Two shapes cover all of them:

```go
	// a bare call
	_, _ = fmt.Fprintf(os.Stderr, "...")

	// a deferred close
	defer func() { _ = conn.Close() }()
```

**Three of these deserve a moment's thought rather than the mechanical
edit**, and your report should say what you concluded about each:

- `internal/mcjoin/mcjoin.go:276` and `:612` are in production code, not a
  test. A `Close` whose error is discarded on a **write** path can lose data
  that was only buffered. Establish whether either is a write path before
  choosing `_ =`; if one is, the honest fix may be to return or log the
  error, and that is a different edit.
- `internal/slp/slp.go:88` is likewise production code.

For the rest — `fmt.Fprintf` to a already-failing stderr path, and `Close` on
a read side or in a test — `_ =` is the right answer and says "we looked".

Expected: 7 issues, all `staticcheck`. Task 3 takes those.


Expected: green. An `errcheck` fix that changes behaviour is a mistake, and

### Task 3: The seven `staticcheck` findings, two of which are not lint

**Files:**
- Modify: `api/v1alpha1/groupversion_info.go`,
  `internal/controller/proxygroup_controller.go`,
  `internal/controller/proxygroup_controller_test.go`,
  `internal/controller/server_controller.go`,
  `internal/controller/server_controller_test.go`,
  `internal/controller/servergroup_controller.go`

**Interfaces:**
- Consumes: `.golangci.yml` from Task 2.
- Produces: `make lint` exits 0. Task 4 makes it blocking.

- [ ] **Step 1: The four `QF1008` and the one `QF1001`**

```
internal/controller/server_controller.go:858:7        QF1008
internal/controller/server_controller_test.go:169:26  QF1008
internal/controller/server_controller_test.go:208:35  QF1008
internal/controller/servergroup_controller.go:529:32  QF1008
internal/controller/proxygroup_controller.go:490:9    QF1001
```

`QF1008` is an embedded `Time` field named explicitly in a selector —
`now.Time.Sub(...)` where `now.Sub(...)` reads the same. Drop the `.Time`.

`QF1001` is `return !(snap.Players == 0 && !snap.PlayersStale &&
snap.Connected)` at `proxygroup_controller.go:490`. De Morgan's law gives an
equivalent without the leading negation. **Read the surrounding function and
its comment before rewriting it**: a negated conjunction sometimes reads
closer to the sentence the code is implementing than its expansion does, and
if that is the case here, the honest resolution is to leave the shape and say
why — see Step 3's note on `//nolint`.

- [ ] **Step 2: `SA4006` — a test smell, not a lint annoyance**

`internal/controller/proxygroup_controller_test.go:476`: a `group` value is
created by `f.createProxyGroup("gateway", ...)` and never used.

**Do not delete the variable and move on.** Read the whole test. There are
three possibilities and they have different fixes: an assertion about `group`
was meant to follow and is missing; the call is needed for its side effect
(it creates an object in envtest) and only the return value is surplus, in
which case the assignment goes and the call stays; or the whole line is
left over from an earlier shape and the test does not need it at all.

Say in your report which it was, and how you established it. If it is the
first, the fix is a new assertion and not a deletion — and that assertion
needs a mutation to show it can fail, like any other.

- [ ] **Step 3: `SA1019` — the one that stays, with a reason**

`api/v1alpha1/groupversion_info.go:32`: `scheme.Builder` is deprecated.
controller-runtime's deprecation text says api packages should have minimal
dependencies, and offers no drop-in replacement.

Establish what the actual alternative is — read controller-runtime's own
docs or the deprecation's suggested path — before writing anything. Then:

```go
	// SchemeBuilder registers this group's types.
	//
	// scheme.Builder is deprecated: controller-runtime's own note says api
	// packages should carry minimal dependencies and this helper pulls in
	// more than that. <State the alternative you found, and what adopting it
	// would cost here.> Silenced rather than migrated because <your reason>.
	//nolint:staticcheck // deprecated scheme.Builder; see above
	SchemeBuilder = &scheme.Builder{GroupVersion: GroupVersion}
```

**The reason is the deliverable, not the directive.** A `//nolint` whose
comment says "deprecated" and nothing else is a silenced finding; one that
says what the replacement is and why it was not taken is a recorded decision.
This is the milestone's only `//nolint` and the acceptance criteria say so.

- [ ] **Step 4: Verify**

```
nix develop -c make lint
nix develop -c make test
```

Expected: `make lint` exits 0 with no output. `make test` green — the
`QF1008` and `QF1001` edits are behaviour-preserving by construction, and
this is what proves it.

- [ ] **Step 5: Mutate, and report what happened**

1. Re-introduce one `QF1008` — put `.Time` back in
   `servergroup_controller.go:529`. Expected: `make lint` reports 1 issue.
   Revert.
2. Change the `//nolint:staticcheck` on `SchemeBuilder` to a bare `//nolint`.
   Expected: **judge this one.** Some golangci-lint configurations require
   an explicit linter name and a reason; others accept a bare directive.
   Report what yours does, because if a bare `//nolint` silences everything on
   that line, that is worth knowing and worth a `nolintlint` note in
   `.golangci.yml` for a later milestone.

- [ ] **Step 6: Commit**

Subject: `fix(6e): the six that were style, and the one that was a decision`.

### Task 5: The `e2e` job

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: Task 1's job shape.
- Produces: the fourth blocking job. Nothing later consumes it.

**What this task is really testing.** `hack/e2e.sh` names podman only in a
comment at `:11-16`, describing how the *caller* invokes it on the author's
machine. Nothing in the script selects a provider, so under a hosted runner's
Docker it is expected to work unchanged. That is an expectation, not a
measurement — this task is the measurement.

- [ ] **Step 1: Read the script's assumptions**

```
nix develop -c sed -n '1,60p' hack/e2e.sh
nix develop -c grep -n "kind create\|kind load\|helm install\|rollout status" hack/e2e.sh
```

Note what it needs: `kind`, `kubectl`, `helm`, a container runtime, and a
`nix build` of the operator image which it then `kind load`s. A hosted
`ubuntu-latest` runner has Docker running already.

- [ ] **Step 2: Add the job**

```yaml
  e2e:
    runs-on: ubuntu-latest
    # hack/e2e.sh builds the operator image with Nix, creates a kind cluster,
    # loads the image, helm installs the chart into platform-system and runs
    # eighteen scenarios. On the author's machine the Go test time alone is
    # about 140s; the image build and cluster creation dominate a cold run.
    timeout-minutes: 45
    steps:
      - uses: actions/checkout@v4
      - name: Install Nix
        uses: cachix/install-nix-action@v27
        with:
          extra_nix_config: |
            experimental-features = nix-command flakes
      # No KIND_EXPERIMENTAL_PROVIDER and no systemd-run: those belong to the
      # rootless-podman invocation hack/e2e.sh documents for the author's
      # machine. A hosted runner has a Docker daemon, which is kind's default.
      - name: make e2e
        run: nix develop -c make e2e
```

- [ ] **Step 3: Push and watch — and expect this one to need iteration**

```
git add .github/workflows/ci.yml && git commit && git push
nix develop -c gh run watch --exit-status
```

The other three jobs run a Go toolchain. This one builds an OCI image, starts
a cluster and installs a chart. If it fails, the log is the answer and the
categories are different from Task 1's:

- **Disk.** A hosted runner has limited free space and the operator image plus
  a kind node image is not nothing. `df -h` in a step tells you. If this is
  the cause, say so — the answer may be freeing space rather than changing
  the script.
- **The image never reaches the cluster.** `kind load image-archive` is
  provider-sensitive in ways `kind create` is not. Read what the script does
  at that point before changing it.
- **A timeout inside the script**, not the job. `hack/e2e.sh` has its own
  deadlines (`DEADLINE`, and `rollout status --timeout`). A runner slower than
  the author's machine can exceed one that has never been near its limit
  locally. **Raising such a deadline is a legitimate fix, and it must be
  reported as one**, with the observed duration beside the new value — a
  deadline raised past a real defect is how a suite goes green while measuring
  nothing.

**If the script needs a change, that change is in scope.** Make it, keep it
minimal, and record what it was and why in your report. The design's §2.2 says
the assumption is that it does not; if that assumption is wrong, saying so
plainly is the deliverable.

- [ ] **Step 4: Confirm what the green run actually contains**

A green job is not the claim. From the run's log, record: the number of
scenarios that ran, that `theOperatorWasNeverDenied` was last and passed, and
the wall-clock time of the job. Eighteen is the expected count.

- [ ] **Step 5: Commit and report**

Subject: `ci(6e): eighteen scenarios, on somebody else's container runtime`.
The body should state plainly that from this point nothing automatic
exercises the rootless-podman path, and that CI proves Docker while the
author's machine proves podman.

### Task 6: The nightly, and the release

**Files:**
- Create: `.github/workflows/nightly.yml`, `.github/workflows/release.yml`

**Interfaces:**
- Consumes: Task 1's job shape.
- Produces: nothing later consumes these.

- [ ] **Step 1: Write the nightly**

```yaml
name: Nightly

on:
  schedule:
    # 03:17 UTC. The odd minute is deliberate: the top of an hour is when
    # every other repository's cron fires, and a job that waits in a queue
    # for its runner is a job whose duration measures the queue.
    - cron: "17 3 * * *"
```

## Notes for the executor

**On pushing.** Four of these seven tasks cannot be verified without pushing
the branch to `origin` and watching a run. That is not optional and it is not
a shortcut being taken — a GitHub Actions workflow has no local execution
model worth trusting. Push the working branch. Never push `master`, never
merge, and never push a tag: a `v*` tag triggers a real publish under the
project's name, and that is the repository owner's decision.

**On the review loop.** This project's record across milestones 5, 6b, 6c and
6d is more than twenty findings, and the great majority came from mutation
rather than reading — including several in test code the plan specified
verbatim, this plan's author's included. Treat every block above as a proposal
that has not been run. When a check you were told to expect to fail does not
fail, that is the finding, and it outranks finishing on time.

**On what CI is worth.** Running a check more often does not make it stronger.
`chart-lint` catches neither half of a typo'd `{{ .Release.Namespace }}` —
milestone 6d measured that — and putting it in a pipeline changes nothing
about what it can see. The value 6e adds is frequency and independence: a
second container runtime, a second machine, and a schedule that does not
depend on somebody remembering. Say that, and do not let a document say more.
