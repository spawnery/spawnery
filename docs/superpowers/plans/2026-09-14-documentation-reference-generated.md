# Documentation site, phase 2: the generated reference Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give `docs.spawnery.cloud` a reference section that cannot go stale, because every page in it is written by a script from the artefact it describes, committed, and diffed by CI.

**Architecture:** Three generators read `config/crd/bases/*.yaml`, `charts/spawnery/values.schema.json` and the operator's own Prometheus registry, and write Markdown into `docs/reference/`. `make manifests` calls them immediately after `hack/chart-templates.sh`, so the reference moves with the schema the way `charts/spawnery/templates/crds.yaml` already does, and CI's existing "the generated files are in step with their sources" step fails a commit that forgot. The one page that cannot be generated — the operator's flags, whose meaning is not in their usage strings — is hand-written and held in step by a Go test that reads `main.go`.

**Tech Stack:** Python 3 with PyYAML (pinned into the dev shell by this plan), Go, Gradle's `:api:javadoc`, Nix, MkDocs Material.

**Spec:** `docs/superpowers/specs/2026-09-14-documentation-site-design.md` — its "The reference is generated" section is the authority this plan argues from.

## Global Constraints

- **Everything committed is English:** page text, commit messages, comments, identifiers. The conversation is German; artefacts are not.
- **Conventional Commits with a scope**, subject says what changed, body says why, wrapped at 72 columns, ending with the two attribution lines the session provides.
- **Comments must earn their place.** The default is no comment. Explain foreign-system behaviour, deliberate absences, numbers that would look arbitrary, or why the obvious approach was not taken — never that a line exists or that something was fixed.
- **Every generated file carries a header naming its generator**, in the exact shape `charts/spawnery/templates/crds.yaml` uses: *Generated by `hack/<script>` via `make manifests`. Do not edit: your changes are lost the next time it runs.*
- **Every load-bearing script in `hack/` has a `-test.sh` companion.** Follow `hack/chart-templates.sh` and `hack/toolchain-pins-agree.sh` plus their tests for the register.
- **Nix reads the git index, not the working tree.** `git add` new files before any `nix build`.
- **Every command runs in the dev shell:** `nix develop -c <command>` from the repository root, no `cd` before the `nix`, no `--extra-experimental-features`.
- **This is the development VM** (8 cores, 8 GB) unless `hostname` says otherwise. `go test` wants `-p 1` here; container work wants `CONTAINER=podman` and `TMPDIR="$HOME/.cache/spawnery-tmp"`.
- **The site must keep building:** `nix develop -c make docs` stays green, which means every new page is in `mkdocs.yml`'s nav and every internal link resolves.
- **The generators' bodies are yours to design, not to transcribe.** This plan fixes each one's inputs, outputs, header, stop-list and test cases, because those are the contract. It does not hand you the parsing code: a two-hundred-line Python program written blind into a plan would be a bug you inherit rather than one you catch. The tests in each task are what pin the behaviour — write them first and let them fail.
- **`docs/assets/mermaid.min.js` is gitignored**; `hack/vendor-mermaid.sh` puts it there. A bare `mkdocs build` without it fails loudly naming the file.

### Task 1: The CRD reference

The largest gap the spec names: `spec.expose`, `spec.routing`, `spec.resources`, `spec.maxPlayers`, `spec.type` and `spec.config` appear in no page today.

**Files:**
- Create: `hack/crd-docs.sh`, `hack/crd-docs-test.sh`
- Create: `docs/reference/crds.md` (generated)
- Modify: `flake.nix` (dev shell), `Makefile` (the `manifests` target), `mkdocs.yml` (nav)

**Interfaces:**
- Consumes: `config/crd/bases/*.yaml`, which `make manifests` has just written with controller-gen.
- Produces: `docs/reference/crds.md`, and the precedent every later generator in this plan follows — header shape, stop-list idiom, test companion.

- [ ] **Step 1: Pin Python into the dev shell, and say why**

`python3` and PyYAML are reachable in the shell today **only by accident** — they arrive inside `python3Packages.mkdocs`'s closure. A generator that depends on that breaks the day mkdocs changes its dependencies, with an error that names neither cause. Add to `flake.nix`'s `packages` list, beside the mkdocs entries:

```nix
              # Explicit, not incidental: python3 and pyyaml are reachable
              # through mkdocs's own closure today, and hack/crd-docs.sh would
              # start failing on a mkdocs bump that dropped them, naming
              # neither cause.
              python3
              python3Packages.pyyaml
```

- [ ] **Step 2: Write the failing test first**

`hack/crd-docs-test.sh`, in the shape of `hack/chart-templates.sh`'s own test. It must assert at least these, each as a named case that prints what it expected:

1. Running `hack/crd-docs.sh` twice produces identical output (idempotent).
2. The output names all five kinds: `Network`, `ServerGroup`, `ProxyGroup`, `Server`, `ScaleBoost`.
3. The output carries the six fields the spec names as missing today: `expose`, `routing`, `resources`, `maxPlayers`, `type`, `config`.
4. **Every path in the generator's stop-list still exists in the CRDs.** This is the case that matters most — see Step 4.
5. The generated file's first line is the "Generated by" header.

- [ ] **Step 3: Run it and watch it fail**

Run: `nix develop -c ./hack/crd-docs-test.sh`

Expected: FAIL at the first case, `hack/crd-docs.sh: No such file or directory`. Record the output.

- [ ] **Step 4: Write `hack/crd-docs.sh`**

A bash wrapper around an embedded Python program, the way a `hack/` script stays the entry point while the parsing lives somewhere that can parse. It reads every `config/crd/bases/*.yaml` and writes `docs/reference/crds.md`.

**The design decision this task exists to get right.** The five CRDs carry **602 properties**, and 97 of them sit under `spec.scheduling.affinity` alone, 21 under `spec.env[].valueFrom`. Those are Kubernetes' own types, embedded by reference — rendering them inline would bury spawnery's ~250 real fields under upstream API surface the reader already has better documentation for.

So the generator carries a **stop-list**: paths whose subtree is not expanded, rendered instead as one row naming the upstream type and linking to the Kubernetes API reference. Discover the real list from the data rather than trusting this one, but it is at least:

```
spec.scheduling.affinity
spec.scheduling.tolerations
spec.defaults.scheduling.affinity
spec.defaults.scheduling.tolerations
spec.resources
spec.env[].valueFrom
```

The stop-list is hand-maintained, and that is deliberate — the same bargain `internal/rbacaudit/required.go` makes. Test case 4 is what keeps it honest: a renamed or removed field turns the test red instead of silently expanding two hundred rows into the page.

For each kind, emit: the kind, its scope and short names, its `additionalPrinterColumns` (three to eight per kind — they are what `kubectl get` shows and nothing documents them today), then a table of `spec` fields with type, required, default and the `description` controller-gen took from the Go doc comment. Emit `status` fields under their own heading; they are read, not written.

Wrap each kind's table in a container the site can scroll horizontally — the spec's layout rules allow a table to exceed the text column only inside its own `overflow-x: auto`.

- [ ] **Step 5: Run the test and watch it pass**

Run: `nix develop -c ./hack/crd-docs-test.sh`

Expected: PASS, every case. Then read the generated page yourself: `nix develop -c head -60 docs/reference/crds.md`. A generator that passes its tests and emits an unreadable page has not done the job.

- [ ] **Step 6: Prove the stop-list test bites, in a throwaway worktree**

A test that is always green looks from the inside exactly like one that passed.

```bash
git worktree add --detach /tmp/crd-mutation
cd /tmp/crd-mutation
# Rename one stop-list path in the CRD, as a field rename would.
sed -i 's/^                  affinity:/                  affinityX:/' config/crd/bases/spawnery.cloud_servergroups.yaml
./hack/crd-docs-test.sh 2>&1 | tail -20
```

Expected: FAIL, naming the stop-list path that no longer resolves. Record it. Then:

```bash
cd /home/paul/git/spawnery
git worktree remove --force /tmp/crd-mutation
```

- [ ] **Step 7: Wire it into `make manifests` and the nav**

In the `Makefile`, after `./hack/chart-templates.sh`:

```make
	./hack/crd-docs.sh
```

In `mkdocs.yml`, under `Reference`, above `Known issues`:

```yaml
      - Custom resources: reference/crds.md
```

- [ ] **Step 8: Verify the whole loop**

```bash
nix develop -c make manifests
git status --porcelain          # expect: nothing, on a second run
nix develop -c make docs        # the site still builds, --strict
```

Expected: `make manifests` run twice leaves no diff; `make docs` green.

- [ ] **Step 9: Commit**

```bash
git add flake.nix Makefile mkdocs.yml hack/crd-docs.sh hack/crd-docs-test.sh docs/reference/crds.md
git commit -m "docs(reference): the CRD reference is generated from the CRDs"
```

### Task 2: The chart values reference

**Files:**
- Create: `hack/chart-values-docs.sh`, `hack/chart-values-docs-test.sh`
- Create: `docs/reference/chart-values.md` (generated)
- Modify: `Makefile`, `mkdocs.yml`

**Interfaces:**
- Consumes: `charts/spawnery/values.schema.json`, and the header and test conventions Task 1 established.
- Produces: `docs/reference/chart-values.md`.

- [ ] **Step 1: Write the failing test first**

`hack/chart-values-docs-test.sh`, asserting:

1. Idempotent across two runs.
2. **Every leaf in `values.schema.json` appears in the page.** Walk the schema in the test itself rather than hard-coding a list — that is what makes the test outlive the next field.
3. Every default shown matches `charts/spawnery/values.yaml` for the same key. A reference that disagrees with the shipped defaults is worse than none.
4. The "Generated by" header is the first line.

- [ ] **Step 2: Run it, watch it fail**

- [ ] **Step 3: Write the generator**

Walk `values.schema.json`, emit one table row per leaf: the dotted key, its type, its default from `values.yaml`, and its `description`. The schema's descriptions are unusually good — several explain a foreign system's behaviour (`leaderElect` being a bool and not the YAML string `yes`; `interval` being a Prometheus duration and not a Go one) — so carry them through verbatim rather than summarising.

`networkNamespaces` is an array with a description that matters more than the type does; make sure an array-typed key renders its description rather than being skipped as having no leaves.

- [ ] **Step 4: Run the test, watch it pass, then read the page**

Run: `nix develop -c ./hack/chart-values-docs-test.sh` — PASS. Then read `docs/reference/chart-values.md` and check it against `helm show values charts/spawnery` for anything that reads wrong.

- [ ] **Step 5: Prove case 3 bites**

- [ ] **Step 6: Wire and verify**

`Makefile` after `crd-docs.sh`; `mkdocs.yml` nav entry `Chart values: reference/chart-values.md`. Then `make manifests` twice with no diff, and `make docs` green.

### Task 3: Metrics and alerts

**Files:**
- Create: `internal/docsgen/metrics/main.go`, `hack/metrics-docs.sh`, `hack/metrics-docs-test.sh`
- Create: `docs/reference/metrics-and-alerts.md` (generated)
- Modify: `Makefile`, `mkdocs.yml`

**Interfaces:**
- Consumes: the operator's own metric registrations, and `charts/spawnery/templates/prometheusrule.yaml` through `helm template`.
- Produces: `docs/reference/metrics-and-alerts.md`.

- [ ] **Step 1: Understand what you are reading before you write anything**

Two sources, and each has a trap.

**The metrics** are registered by `init()`-time `var` blocks in `internal/certs/metrics.go`, `internal/grpcauth/metrics.go`, `internal/serverreg/metrics.go`, `internal/agentserver/metrics.go` and their siblings, into controller-runtime's `metrics.Registry`. **Do not parse the Go source.** A program that imports those packages and calls `metrics.Registry.Gather()` gets the real name, type and `Help` string of every metric actually registered — which is the thing a reader needs, and which cannot drift from the code because it *is* the code.

A gauge that has never been set may not appear in `Gather()`'s output. Check this: if it bites, use `prometheus.Registry`'s `Describe` path instead of `Gather`, which reports descriptors whether or not a sample exists. Say in your report which one you used and why.

**The alerts** live in a Helm template with ten `{{ }}` expressions, so it is not YAML until Helm has rendered it. Run `helm template` over `charts/spawnery` with `metrics.prometheusRule.enabled=true` and parse the output. The alert whose `summary` interpolates `caExpiryWarningDays` will render with the default value — note in the page that the number comes from a chart value, rather than presenting it as fixed.

- [ ] **Step 2: Write the failing test first**

`hack/metrics-docs-test.sh`, asserting:

1. Idempotent across two runs.
2. **Every metric name that appears in a `prometheusrule.yaml` alert expression also appears in the metrics table.** This is the case worth having: an alert on a metric the operator does not export is a rule that never fires, and nothing else in this repository checks it.
3. Every alert in the rendered PrometheusRule appears in the page with its `severity` and `for` duration.
4. The "Generated by" header is the first line.

- [ ] **Step 3: Run it, watch it fail.** Record the output.

- [ ] **Step 4: Write `internal/docsgen/metrics/main.go`**

Imports the metric packages for their registration side effect, gathers the registry, and prints a Markdown table: name, type, labels, help. Deterministic order — sort by name, or two runs will differ and Task 3's own idempotency case will fail intermittently, which is worse than failing always.

`internal/docsgen/` rather than `cmd/`: `cmd/` holds binaries that ship in an image plus two named test-only ones, and a documentation generator is neither. Say so in a comment at the top of the file, because the placement is a choice a reader would otherwise question.

- [ ] **Step 5: Write `hack/metrics-docs.sh`**

It runs `go run ./internal/docsgen/metrics`, runs `helm template` for the alerts, and assembles both into `docs/reference/metrics-and-alerts.md` with the standard header.

- [ ] **Step 6: Run the test, watch it pass, read the page**

Then cross-check by hand: the page's metric list against `grep -rn 'Name: "spawnery_' internal/`. If the generated list is shorter, a package is not imported; if longer, something registers a metric nobody documented. Either way, say which in your report.

- [ ] **Step 7: Prove case 2 bites**

In a throwaway worktree, add an alert to `charts/spawnery/templates/prometheusrule.yaml` on a metric that does not exist (`spawnery_does_not_exist > 0`), and confirm the test fails naming it. Record the output, remove the worktree.

- [ ] **Step 8: Wire and verify.** `Makefile`, `mkdocs.yml` nav (`Metrics and alerts: reference/metrics-and-alerts.md`), `make manifests` twice with no diff, `make docs` green.

- [ ] **Step 9: Commit**

```bash
git commit -m "docs(reference): metrics and alerts, from the registry and the rule"
```

### Task 4: The operator's flags, and the test that keeps the page honest

The one reference page that cannot be generated: a flag's meaning is not in its usage string, and the seventeen flags in `cmd/spawnery-operator/main.go` are documented nowhere at all today.

**Files:**
- Create: `docs/reference/operator-flags.md` (hand-written)
- Create: `cmd/spawnery-operator/flags_docs_test.go`
- Modify: `mkdocs.yml`

**Interfaces:**
- Consumes: `cmd/spawnery-operator/main.go`, read as source.
- Produces: a page, and a red test the day somebody adds a flag without documenting it.

- [ ] **Step 1: Write the failing test first**

`cmd/spawnery-operator/flags_docs_test.go`, in the idiom this repository already uses for constants that cross a boundary — `internal/podspec/env_test.go` and `internal/agentpb/contract_test.go` both read a file rather than importing a symbol. Read `main.go`, extract every flag name from the `flag.StringVar` / `BoolVar` / `DurationVar` / `IntVar` / `Var` calls, read `docs/reference/operator-flags.md`, and fail naming any flag absent from the page.

Two things to get right:

- **Parse, do not regex loosely.** `go/ast` is in the standard library and the file is small; a regex that misses `flag.Var(&drainTaints, "drain-taint", …)` because it takes a pointer to a custom type gives a test that passes while the page is wrong.
- **Fail in both directions.** A flag removed from `main.go` but left in the page is the same defect wearing the other face.

- [ ] **Step 2: Run it, watch it fail**

Run: `nix develop -c go test ./cmd/spawnery-operator/ -run TestFlagsAreDocumented -count=1`

Expected: FAIL, listing all seventeen flags as undocumented because the page does not exist. Record the output.

- [ ] **Step 3: Write the page**

One section per flag: the flag, its default, and what it *does* — which is the part the usage string does not carry. `main.go`'s surrounding comments are the source; read them rather than paraphrasing the usage strings.

Four of the seventeen deserve more than a line, and the page is worth writing for these alone:

- `--allow-plugin-volumes`, `--allow-file-volumes`, `--allow-mount-volumes` — three switches gating three claim-backed sources, whose relationship is exactly the thing a reader gets wrong. `docs/guides/plugins-from-a-volume.md` and `docs/guides/mounts-and-files.md` carry the detail; link, do not restate.
- `--drain-taint` — repeatable, and what it means for a group that cannot replace what it condemns.

Say plainly that none of the three `--allow-*` flags is a security control, because the chart's own schema says so and a reference page that omits it invites the opposite reading.

- [ ] **Step 4: Run the test, watch it pass**

Run: `nix develop -c go test ./cmd/spawnery-operator/ -run TestFlagsAreDocumented -count=1` — PASS.

- [ ] **Step 5: Prove it bites, in a throwaway worktree**

Add a flag to `main.go` without touching the page; confirm the test fails naming it. Then remove the flag, delete a flag's section from the page instead, and confirm it fails in the other direction too. Record both. Remove the worktree.

- [ ] **Step 6: Wire and verify.** `mkdocs.yml` nav (`Operator flags: reference/operator-flags.md`), `make docs` green, and `nix develop -c go test -p 1 ./cmd/...` green.

- [ ] **Step 7: Commit**

```bash
git commit -m "docs(reference): the operator's flags, and a test that keeps them listed"
```

### Task 5: CI fails a commit that forgot to regenerate

Three generators now run inside `make manifests`. Nothing yet proves CI notices when they are skipped.

**Files:**
- Modify: `.github/workflows/ci.yml` (the "the generated files are in step with their sources" step)

**Interfaces:**
- Consumes: the three generators from Tasks 1-3.
- Produces: a red build for a commit that changed a CRD without regenerating its reference.

- [ ] **Step 1: Understand what the step catches and what it does not**

`.github/workflows/ci.yml:82` is two checks, and only one of them reaches the new pages.

`git diff --exit-code` is unscoped, so it already catches a **modified** `docs/reference/*.md` — and it will run the generators, because `make test` depends on `manifests`. That half needs no change.

The second check does not. It looks for files generation *added* but nobody committed, and it is scoped `-- api config charts`. Its own comment explains why that case exists: "git diff sees nothing when generation adds a file — a new CRD, for instance, which is exactly the change most likely to be forgotten." A first run of a new generator, or a generator that starts emitting a page it did not before, is that same case and falls outside the scope.

- [ ] **Step 2: Widen the untracked check**

Add `docs/reference` to that path list. Leave the failure message alone: it already names what to run, which is what the person reading CI needs.

- [ ] **Step 3: Prove it, and this is the whole task**

A CI guard nobody has seen fail is a guard nobody knows works. In a throwaway worktree, change one CRD's Go doc comment, run `make manifests` so the CRD yaml moves but revert only `docs/reference/crds.md`, then run exactly what CI runs and confirm it fails naming that file. Record the command and the output verbatim.

- [ ] **Step 4: Commit** (or report that no change was needed, with the evidence from Step 3.)

### Task 6: The Javadoc, built into the site

Pulled forward from phase 4 because it is build work and this plan is where build work lives. `agent/api/README.md` and the prose pages stay in phase 4.

**Files:**
- Create: `nix/agent-api-javadoc.nix`
- Modify: `flake.nix`, `nix/docs-site.nix`, `mkdocs.yml`

**Interfaces:**
- Consumes: `agent/api/src`, `agent/deps.json`, and the `docs-site` derivation from phase 1.
- Produces: the site carrying `/plugin-api/javadoc/`.

- [ ] **Step 1: Decide the shape before building, and say why in the report**

`agent/api/build.gradle.kts` already sets `withJavadocJar()`, so the task exists; what is needed is the HTML tree, not the jar.

The obvious route — take `agents` as an input to `docs-site` — is wrong, and the reason is a number: `nix build .#agents` builds both plugins against the Paper and Velocity jars and runs two JUnit suites, where `make docs` currently takes 43 seconds in CI. Putting that in front of every documentation build trades a fast link check for a slow one.

So: a derivation that builds `:api:javadoc` alone. `agent/api` depends on nothing but the JDK and, for tests only, JUnit — read `agent/api/build.gradle.kts` to confirm before relying on it. Reuse `nix/agents.nix`'s Maven lockfile mechanism (`agent/deps.json`); read that file for how the offline cache is wired.

**If a javadoc-only derivation turns out to need the whole agents machinery**, do not force it. Fall back to exposing the javadoc as its own flake attribute that `nix/docs-image.nix` consumes while `docs-site` does not, so `make docs` stays fast and the published site still carries the Javadoc. Report which of the two you ended up with and what decided it.

- [ ] **Step 2: Build it and look at the output**

```bash
git add nix/agent-api-javadoc.nix flake.nix
nix build .#agent-api-javadoc --no-link --print-out-paths
ls "$(nix build .#agent-api-javadoc --no-link --print-out-paths)"/index.html
```

Expected: a store path carrying `index.html` and `cloud/spawnery/agent/api/SpawneryApi.html`.

- [ ] **Step 3: Put it in the site**

`nix/docs-site.nix` copies the tree to `plugin-api/javadoc/` inside the built site — in `postPatch` beside the mermaid install, or in the build phase, whichever reads better next to what is already there.

MkDocs will not know about those files, and that is correct: they are generated HTML, not pages. Confirm `--strict` does not complain about them; if it does, the fix is `exclude_docs` or placing them outside `docs_dir`, not relaxing `--strict`.

- [ ] **Step 4: Add the nav entry**

Under `Plugin API` — a new top-level section this task creates, holding one entry for now:

```yaml
  - Plugin API:
      - Javadoc: plugin-api/javadoc/index.html
```

Check how MkDocs handles a nav entry pointing at a file it did not render. If it will not, use a small `docs/plugin-api/index.md` that links to it and say so in your report — phase 4 fills that page with prose anyway, so a stub there is not waste.

- [ ] **Step 5: Verify end to end**

```bash
nix develop -c make docs
P=$(nix build .#docs-site --no-link --print-out-paths)
ls "$P/plugin-api/javadoc/index.html"
grep -c 'SpawneryApi' "$P/plugin-api/javadoc/index.html"
```

Then time it: `make docs` should still be close to its current cost. If it is now minutes, Step 1's fallback is the answer and you should take it.

- [ ] **Step 6: Commit**

```bash
git commit -m "docs(site): the plugin API's Javadoc ships with the site"
```

## What this phase does not do

The remaining prose — five missing guides, the plugin API's five prose pages, the three explanation pages, and `docs/history.md` brought forward over the 94 commits since the rollout — needs no plan. Its test is `mkdocs build --strict` and somebody reading it, and the spec already lists every page and what it covers. It is written directly, one page per commit.
